# Native Linux host service fixture

`native/linux/host_services.c` constructs original Linux host service objects for the hash-gated native runtime diagnostic. This is a diagnostic binding into the actual host process, not an initialized gameplay implementation.

The original Linux host has no DWARF. Constructor signatures, object allocation sizes and ownership bindings are verified from this exact host's native dynamic symbols and call sites, summarized in [host-services-abi.json](../evidence/linux/host-services-abi.json). Raw disassembly remains private at `../c6-ghidra/evidence/linux-services/host-construction-database.txt`. No Windows RVAs or layouts are used.

The fixture calls original `operator new`, original `Civ6App` construction and then publishes that object into original `g_pkApplication`, matching native `WinMain`. It refuses an already published App. Original `RunApp` normally initializes the AppEnvironment documents buffer with original `Platform::wcscpy`; the fixture supplies the explicit task directory `target/linux-runtime/userdata` through that same copy API and exact verified buffer. Original `GetUserDirectoryPath` appends the game's directory suffix. This documents directory is an explicit fixture input, not an invented partially constructed App. `HOME` is unchanged. Original `EngineUtility` construction then creates its real scripting, logging and achievements services.

The database fixture repeats original `Civ6App::SetupDatabase` allocations and owning-pointer stores for genuine `ConfigurationDatabase` and `GameplayDatabase` objects. It calls original `Database::Initialize` and original parameterized database `Initialize(cache_path, source_directory)` methods. Source paths select the original lowercased Base asset directories; the built-in parameterless methods contain old mixed-case relative paths. The runner must gate the complete recursive source trees before using `C6_HOST_ASSETS`. No generated SQLite connection, table, return value or service import replaces an original implementation.

Original `FAutoArchiveFactory::CreateInstance` establishes the real factory required by Context autoarchive teardown. Its original `FreeInstance` handles teardown; network services are not initialized.

The cleanup entry point must run after all Context users have been destroyed. It invokes original utility and App destructors, original deallocation and database shutdown, and clears the original App global. The measured [initialization checkpoint](../evidence/linux/runtime-context-initialize-complete.json) executes genuine Context initialization, observes `IsInitialied` change from false to true, destroys the Context and both additional factory-cycle Contexts, completes original service cleanup and closes the GameCore handle with exit zero. This establishes the native service/Context lifecycle, not database contents or gameplay parity. The process uses `_exit` because full host App startup and application shutdown have not run.

The fixture omits localization, content mounting, mod/DLC activation, full host App options, Steam/network, rendering and GUI startup. Base XML bootstrap input identity does not establish DLC or save configuration equivalence. See [runtime evidence](linux-runtime.md) for measured stages, failures and remaining boundaries.

## Original Lua VM and thread diagnostic

`runtime_probe.py --initialize --localization --lua` additionally invokes original `AppLuaScriptSystem::Create`. The native factory allocates and constructs the concrete host system, initializes its genuine Havok Lua VM and publishes original `LuaScriptSystem::Get()`'s singleton. The fixture refuses a pre-existing singleton. Its actual concrete `AppLuaThread` factory receives the same `ThreadType` value 1 used by original `GameCore::ScriptSystem::CreateLuaThread`.

The diagnostic obtains the real child `lua_State`, pushes numeric value 16777215 through original Havok API wrappers, verifies the exact stack increment and numeric result, then restores the original stack top. It calls the original concrete thread deleting destructor, which releases the VM child through the real singleton. Original singleton `Destroy` executes after utility/script-user destruction and clears publication. No synthetic VM, thread, provider import, or host Lua implementation is substituted. [Target-specific ABI evidence](../evidence/linux/host-services-lua-abi.json) records the exact symbols and private disassembly identity.

The [measured Lua lifecycle](../evidence/linux/runtime-lua-context-lifecycle.json) passes with exit zero: genuine singleton/VM construction, child stack roundtrip and release, native Context initialization/destruction, localization shutdown, service/VM destruction and `dlclose`. This validates this isolated native boundary. It does not establish arbitrary Lua execution, complete App Lua libraries, gameplay configuration, save loading or action/turn parity.

## Rules source path fixture

`C6_RULES_SOURCE_ROOT`, when set by the runner's separately gated `--rules-source-view` option, replaces only the configuration/gameplay source directory prefix passed to the original database initializers. Every source file remains byte-identical to its gated original; the private fixture view adapts the original loader's literal `Schema` directory spelling to the supplied asset tree's lowercase `schema` directory. Original assets and native importer code remain unchanged.

This distinction changes measured content: the original raw-path run returned successful initializer booleans while exporting an empty configuration database and eight empty gameplay schema tables. The [case-view cause probe](../evidence/linux/runtime-rules-source-view-cause-probe.json) instead exports 78 configuration tables with 1,280 rows and 318 gameplay tables with 23,966 rows, with original native backups and all source/destination row counts compared. These are measured Base database results; they do not establish XP2/DLC content activation or the saved game's rules/configuration identity. Initializer success and Context startup success alone never establish that the required rows were imported.
