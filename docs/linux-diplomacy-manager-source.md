# Linux diplomacy manager ownership and empty-state boundary

Static inspection of the supplied Linux XP2 module establishes the live containers consumed by `Diplomacy::Manager::ProcessPending`. It does not implement statement processing, loading, a complete action or turns. The [evidence manifest](../evidence/linux/diplomacy-manager-source.json) records complete method fingerprints and selected checked instructions against SHA-256 `a0b6611f45ed28fa7bf6e18d608cafddbdd5b1c20cfd880cb50937af731c1faa`. No original code was executed for this research. Attribution remains in [reference.md](reference.md).

`GameCore::Diplomacy::Manager` operates on module globals; this is distinct from `Diplomacy::Deal::Manager`. Full ELF symbols contain no diplomacy Manager constructor, Read or Write. That absence alone does not prove that every restore path leaves the globals untouched; an exhaustive restore write audit remains open.

| Global | RVA | Representation consumed by native code |
| --- | --- | --- |
| `ms_kOpenSessions` | `0x3c052f8` | 24-byte libc++ list of unique Session pointers |
| `ms_kClosedSessions` | `0x3c05310` | Same list representation |
| `ms_pkActiveSession` | `0x3c05328` | Session pointer |
| `ms_kPendingActions` | `0x3c05330` | 32-byte EASTL vector of 12-byte PendingAction records |

The module initializer `0x1fc4260` calls open-list initialization `0x1fc41a0`, closed-list initialization `0x1fc41d0` and pending-vector initialization `0x1fc4200`. Each list initializer writes its own address into both sentinel links at offsets 0 and 8, and zero into its count at `+0x10`. The vector initialization reaches `VectorBase` constructor `0x2915c80`, which zeros begin, end and capacity pointers. The active pointer is BSS state. This establishes module-construction emptiness; later gameplay can populate these globals.

`Manager::Initialize` (`0x29112c0`, 0x31a bytes) registers names and statement/action factories, enables diplomacy logging, and conditionally subscribes to the game's turn-ended signal. Its complete body contains no session/action container reset. `Uninitialize` (`0x29115f0`) explicitly clears open and closed session lists, clears pending actions, nulls the active pointer and unsubscribes the signal. Calling Initialize does not supply an empty-state witness for a reused module.

The no-argument `HasPendingSessionStatements` (`0x2913f90`) compares the **open-session list count at `ms_kOpenSessions+0x10`** against zero. Despite the name it does not inspect pending statements inside sessions. The historical probe field `open_session_map_nonempty` records this getter: there is no separate map in this path. `ProcessPendingSessionStatement` (`0x2911900`) traverses the same global, using its link at `+8`, following node links at `+8` and reading the node's unique Session pointer at `+0x10`. The standard native list invariant connects the count predicate and that traversal. A live adapter should verify both sentinel links and count for an empty capture, or retain a proven native container invariant; a fabricated zero count is insufficient.

`HasPendingActions` (`0x2913fa0`) obtains the current pending-vector size and tests its 32-bit result. The size body (`0x29155f0`) divides end minus begin by 12. PendingAction's constructor (`0x29151b0`) stores its unsigned identifier and two player enums at offsets 0, 4 and 8. An empty vector can retain allocated capacity; empty does not require all vector pointers to be null. Pending actions are separate from session pending statements and are not consumed by ProcessPending's body.

Session constructor `0x2916d10` constructs three EASTL statement-pointer lists at `+0x10`, `+0x28` and `+0x40`; it does not initialize the scalar prefix. Endpoint getters read the from-player enum at 0 and to-player enum at 4. `RemoveNextPendingStatement` (`0x2917270`) uses the `+0x28` list for OUTGOING direction 1, scans in list order and removes the first matching source (and optional destination). Statement ownership and concrete processing must remain exact. An existing session may have an empty pending list; the no-argument getter still reports its open-session list as nonempty.

`ProcessPending` (`0x2913510`) gets `Player::Manager::GetWasEverAlive`, copies the complete fixed vector of Player pointers and iterates that snapshot in order. `GetWasEverAlive` (`0x24273f0`) returns `PlayerManager+0x3a8`. Its vector header has begin/end/capacity pointers at offsets 0/8/0x10. Copy constructor `0x29152e0` initializes its own inline storage at `+0x28` with end capacity at `+0x228`, then assigns the source begin/end range; overflow is allowed, so capture the actual pointers and contents. `InitializeLists` (`0x2b51c10`) clears the derived lists, scans exactly 64 pointer slots in ascending slot order from the array referenced at `PlayerManager+8`, skips null slots, and appends each player whose current `WasEverAlive` is true. It does not restrict this general list to majors, current survivors or humans; classification-specific lists are populated separately. `WasEverAlive` (`0x2103ff0`) reads the byte at `Player+0x278`. This proves construction order, not that arbitrary later state can reconstruct a current snapshot from just a set of IDs. Preserve the actual pointer/handle list and its current order at the boundary.

For each copied player pointer, ProcessPending reads ID and then current IsAI once. `Player::IsAI` (`0x2b31550`) gets the current global configuration, looks up the configuration player using the player ID field at `+0xe0`, calls configuration IsHuman and inverts it. Configuration IsHuman (`0x28ec230`) is exactly `GetSlotStatus()==3`. `GetSlotStatus` (`0x28ebe70`) reads the SlotStatus variant through the configuration player's data object and returns 2 when absent. `GetPlayerConfiguration` (`0x28e4ea0`) uses the configuration player vector at `+0x90` for unsigned IDs below 64, and the fallback player at `+0x8b8` otherwise. This is a configuration dependency, not a gameplay AI object flag. Preserve that current variant/default semantics and re-read later players after synchronous statement effects. The outgoing drain retains the already-read player ID and does not re-read IsAI between successive statements for the same player.

The existing `core-component-execute-3.json` contains actual `diplomacy_before` and `diplomacy_after` observations with both predicates zero. The manifest pins that public report and its private runtime report. These observations witness an empty native open-session list and pending-action vector at those times, under that historical probe's configuration and intact native containers. They do not prove a current loaded-handler capture has identical runtime state, or that the saved image restores those globals. The report itself retains `gameplay_parity=false` and `full_action_acceptance=0`.

An admissible state-backed empty ProcessPending provider needs the current actual open-session inventory (or its verified empty sentinel/count), the ordered ever-alive player handle snapshot, and current ID/configuration lookup semantics. With a genuinely empty open-session list, each AI player's removal attempt returns false and no ProcessStatement runs; the original player/configuration reads still occur. Supporting nonempty sessions requires actual pending-list state and ProcessStatement routing, history, subtypes, affected state/RNG and external-policy decisions. Nonempty must remain explicitly unsupported until those dependencies exist; no-op success or native AI choice substitution is inadmissible. A future native comparison must capture this complete boundary and its affected state under the exact rules/configuration identity.

The historical **89,198-byte raw Save→Load difference** remains unclassified and unmasked. This research does not close full gameplay state/action/turn parity.
