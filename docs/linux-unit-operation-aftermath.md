# Linux UnitOperation continuation

`unit_operation_aftermath` implements source-derived control flow after the unit manager's `Add` returns. It closes the missing ordering layer between pending diplomacy, notification upkeep and owner blocking. Actual statement, notification subtype, factory and reporting providers remain required; this is not a complete SkipTurn action or full state/action/turn parity. No native code was executed. [The audit](../tools/linux/unit_operation_aftermath_audit.py) and [checked contract](../evidence/linux/unit-operation-aftermath.json) pin the supplied Linux XP2 SHA-256 and original instruction sites. Attribution remains in [reference.md](reference.md).

The caller must preserve the real request's earlier TurnUnready and script/callback reads. The new `after_add` boundary begins only after a valid owner's actual unit has been found and manager Add has returned. Original Execute always runs this aftermath even when Add rejected an operation. Missing player/unit returns before this boundary. No request admission, manager Add, native policy choice or resumable external-policy continuation is supplied here.

`process_pending` copies ever-alive player handles in their original order, reads each player's ID and current IsAI once, then drains that player's outgoing statements. Each attempt starts at the current open-session head, matches the player to either session endpoint, removes the first pending statement whose source matches the player, and calls the required ProcessStatement provider. Removal happens before processing. A statement callback may populate an earlier session or change a later player's IsAI; subsequent reads observe those changes. A typed `Session<S>` retains statement payload ownership in the caller's `S`, without substituting opaque serialized bytes. Full ProcessStatement routing, session history, concrete subtype behavior, diplomacy state/RNG and external decisions remain unresolved. `ExternalDecisionRequired` is an explicit unsupported diagnostic, not a successful native policy yield.

Notification Update runs SendAutoNotify, conditional ProcessAutoActivate, DismissExpired, Cleanup. SendAutoNotify reads definition flags in order, reads a type hash only for an auto definition, calls Create(hash, owner, true, null), skips null results, releases redundant objects, and otherwise invokes virtual InitializeText before Add. It fixes the definition-array end at entry but reads each definition at its actual iteration point. Its provider must preserve the original allocation/end stability. The cloud gate is read through a newly captured configuration after synchronous InitializeText/Add effects. Each created object captures its actual player-notification collection before redundancy; A subtype InitializeText may replace global collection bindings, but Add uses that same retained collection. Later definitions reacquire their collection. ProcessAutoActivate captures Configuration before the AcceptsNotifications callback, checks current AcceptsNotifications and active turn, captures the actual collection before the network getter, computes network threshold 0/3 through the retained configuration, and rescans the same retained collection after every virtual Activate(false), stopping on null or a locked result. It can use the existing `notification_lifecycle::find_auto_activate` only for that function's verified profile. Its combined activation-and-cleanup entry point cannot replace Update because expiration belongs between those phases.

DismissExpired skips records already dismissed, evaluates actual subtype expiration, calls actual virtual Dismiss, then reads the next list-node link after the callback. An explicit Cursor distinguishes native nodes from object identities, including repeated object pointers and duplicate ComponentIDs. Each scan retains its collection and captured end cursor; no hidden provider cursor can be overwritten by reentrant processing. Cleanup is a required concrete provider; `notification_lifecycle::cleanup_in_place` supplies its verified ownership profile. Reporting subscribers are synchronous dependencies and are never excluded by cache, UI, AI or callback names. All genuine player choices must go to an external policy.

The blocking reducer calls actual IsValidForPhase (+0x30), which is distinct from IsNeeded (+0x38), skips zero blocking, and retains the first record with the greatest **unsigned** severity. It reads current severity values at each comparison and calls the selected blocking getter again at the end. Owner Update retains the actual Player receiver. It captures Manager Get/Edit/Get before re-reading that player's current ID for each initial blocking, Update and final blocking call; the turn-complete lookup also re-reads the ID. Its final store uses the retained player, then re-reads ID before local comparison. Owner Update reads blocking before the real turn-complete flag; incomplete owners execute Update and read blocking again. Set stores a changed enum before reading local player and sends event `55f15a7b` with old/new signed enums only for the local owner. Equality skips both store and local-player read. A standalone verified base-expiration helper uses positive signed delta and signed comparison against wrapping added-turn plus delta. It must not replace the thirty subtype expiration overrides.

Provider failure after mutation is possible in each lower-level function, including pending removal before ProcessStatement. `after_add` runs on a cloned candidate and returns it only on success. Its contract requires every mutable effect to be fully owned and isolated by Clone. Shared interior state, native/global callbacks, external I/O and effects cannot satisfy that contract merely by deriving Clone. The API supplies no blanket rollback for them. Diagnostic budgets are explicit errors, never successful native termination. Complete state/RNG, callbacks, queues and ownership must be present in an eventual accepted provider.

Thirteen boundary tests cover pending endpoint filtering/removal, head rescan and later-player IsAI changes, factory null/redundant/InitializeText/Add order, callback-driven cloud changes, activation before expiration/cleanup, unsigned severity ties and final getter reread, complete/equal/store/report gates, rejection isolation and signed wrapping expiry. A repeated-object test checks distinct node traversal. Additional mutation tests replace global configuration and collection bindings during accepts/network/activation/InitializeText callbacks and verify original retained receivers; owner identity tests verify repeated ID reads and Manager capture order. These are Rust control-flow tests, not native differential comparisons. Reproduce the static evidence with:

```sh
python3 tools/linux/unit_operation_aftermath_audit.py \
  --output target/linux/unit-operation-aftermath.json
```

The next concrete closure is a captured-owner adapter for actual expiry/phase-valid/blocking virtual bindings, current game turn and omitted live blocking field `+0x130`, followed by an exact auto-notification definition/factory inventory. Factory effects, statement processing, reporting delivery and complete affected state/RNG need native fixture comparison before this boundary can support an accepted action. The historical **89,198-byte raw Save→Load difference** remains unmasked and unresolved for exact-state restoration; mapped byte owners do not resolve its semantics.

The compatibility provider method `Notifications::send` names the original
virtual `+0x80` **InitializeText** dispatch; its former Send label was incorrect.
All six stock auto-notify subtype slots bind base `0x2d2dd10`, which assigns
definition message/summary. This dispatch does not itself publish a notification
event. `PlayerNotifications::Add` later assigns the new ID, appends the object,
calls `+0x90`, sends actual `f26f3acf`, and expires superseded records. Historical
reports remain preserved; this correction changes labels, not control flow.
