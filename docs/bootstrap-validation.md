# Bootstrap integration checks

Run `python3 tools/check/bootstrap_runtime.py` with local fingerprinted proprietary assets and Wine/MinGW installed. Add `--assets PATH` to use a different asset root. This checks the isolated original Windows context factory boundary; it is not a full Civ VI state/action/turn parity test.

The check computes the runner's current configuration identity before executing it, then supplies that identity with `--expected-configuration`. It starts two separate host processes. Each must report a normal Windows load, exactly three original context constructions, successful queries for both accepted GUIDs, rejection of the unknown GUID, and completed context destruction and GameCore unload. It also checks refusal of a wrong configuration identity and directly runs the native host with incorrect target and original-host files, requiring rejection before loader observations. It checks source hashes, compiler/Wine identity, the configured module/provider allowlist, and rejection of a changed DatabaseDLL or CRT provider.

`python3 tools/check/bootstrap_runtime.py --diagnostics` additionally exercises separately identified initialization and SQL diagnostics. The missing-database mode must stop before Initialize returns. The empty-database and original-schema modes must record a true original Initialize return, an IsInitialized transition from false to true, and successful context destruction and unload across three cycles. The schema mode must execute all seven original SQL sources successfully. A separate raw-byte schema mode must fail at source index 5 with status 15 before Initialize; the missing-database mode retains its expected status 86. These are context and database diagnostics, not initialized gameplay or parity. If the supported boundary changes, update the checks alongside new native evidence rather than accepting any exit status.

The checker uses temporary JSON reports and does not rewrite the committed evidence corpus. Source changes invalidate old configuration identities; new native observations must be regenerated after the host and services reach a coherent checkpoint. The runner records its executable hash separately from source/configuration identity. A successful factory check does not establish rules population, database contents, enabled DLC/mod configuration, script execution, legal actions, save loading or turn advancement.

The runner and check impose process timeouts. They do not prove cancellation of every Wine subprocess on timeout, concurrency isolation of a shared Wine prefix/build directory, or protection against trusted local assets changing between hash and load. Run bootstrap checks serially. The original executable is mapped without its CRT/entry point solely for the evidenced empty-string getter; these checks do not extend that narrow host-export contract.
