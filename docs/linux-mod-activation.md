# Original Linux mod activation boundary

The genuine Linux host now completes its original XP2 Configure/Update content pipeline, exports repeatable native configuration/gameplay databases, and cleans up its constructed providers. The fixture uses a constructor-state censorship callback and a renderer-uninitialized UI provider. Proper saved Request/Begin/finalization, action and turn parity remain unproven; the c6 simulator still implements isolated primitives. Lower Core Load/Save and selected read-only native state queries have separate [bounded evidence](linux-game-load.md).

The starting reference is cru121's pinned [host architecture research](https://github.com/cru121/civ6-gamecore-reference/blob/5af389445118bed2bdebf7a8a42b219c8fba5175/findings/topics/exe-gamecore-architecture.md) and [host function index](https://github.com/cru121/civ6-gamecore-reference/blob/5af389445118bed2bdebf7a8a42b219c8fba5175/reference/data/exe_function_index.json). Those identify `InitInstance`, `BootstrapContent`, `ConfigureContent`, `UpdateContent` and the real importer families. New lifecycle, return-ABI and provider findings below come from instructions and bounded Ghidra decompilation of the supplied **Linux host**, SHA-256 `106d4986567cf60aad787dfac990d089e41775e04b5f40e073f59a3a8ffe74f4`, then measured native execution. The host does not provide the GameCore library's DWARF type definitions; host ABI findings here are not described as DWARF proof. No Windows calling convention, importer sequence or content eligibility is transferred.

## Construction and ownership

`AppModdingFramework::InitInstance()` (`0x33853e0`) returns bool. It allocates `0x300` bytes through the original allocator, calls the full original constructor (`0x337c980`), and only then publishes the original singleton. The constructor initializes its native modding database, file/discovery/logger/ownership services and handlers, discovers mods, subscribes to host events, and invokes `BootstrapContent()` at `0x337e11c` **before singleton publication**.

`BootstrapContent()` (`0x337f090`) selects/loads the initial GameCore, initializes the original gameplay database, injects native GameCore database metadata, invokes `InitializeGameCore()`, and constructs original UI/telemetry/view support objects. Consequently InitInstance is not an isolated registry constructor. It must precede any separately factory-created context. In the passing measured fixture it loads the hash-gated **Base** library, and both original `GetDLLPath` and `dladdr` on the actual context vptr identify that Base library.

`c6_linux_mod_framework_initialize(void **borrowed_context)` in [mod_activation.c](../native/linux/mod_activation.c) observes the genuine exported active-context global after native construction. The returned context is borrowed. Do not pass it to a standalone `DllDestroyGameContext`, retain it across `UpdateContent`, or run a second independent Initialize lifecycle on it.

Another ABI trap is `GameCore::GetContext()` (`0x31dd790`): its C++ return wrapper uses a hidden output pointer in RDI. It is not callable as `void *(*)(void)`. The adapter avoids constructing or guessing that wrapper.

The adapter first calls genuine `AppModdingFramework::UnloadGameCore()` while the host configuration manager is alive, then calls `AppModdingFramework::DestroyInstance()` and `GameCoreController::Shutdown()`. The latter two calls follow original `Civ6App::GUIShutdown` call sites `0x2f98190` and `0x2f98195`. The original framework destructor unsubscribes its events, shuts down configuration, releases the controller's context, unloads GameCore, clears native UI/telemetry/view owners and shuts down the framework. The tested fixture then shuts down its constructor-only client, host providers and ASL filesystem. Native observations verify framework/context/controller/client/application owners become null. This covers those constructed providers, not the entire GUI application's Startup/Shutdown.

The real external client constructor is `AppFiraxisLiveClient::AppFiraxisLiveClient(char const*)` (`0x3199cc0`), size `0x218` at the original Startup allocation site. Its nested base constructor initializes containers/strings and leaves the actual external client uninitialized; its local telemetry manager parses embedded configuration. The fixture invokes this constructor with the original `Civ6` name constant and the original libc++ shared_ptr constructor (`0x31a8b60`) on the actual empty singleton owner. It does not fabricate a getter or object fields.

The full `AppFiraxisLiveClient::Startup` would proceed to Steam account APIs and service initialization, so the fixture does not invoke it or publish application events. An independent native constructor/cleanup run checks that the actual getter identifies the constructed object, original `IsInitialized` remains false, and original `Shutdown` unpublishes the owner and completes. In that state the original Shutdown's connection check avoids its telemetry flush branch. This intentionally unstarted external service is a fixture limit, not full host Startup.

## Filesystem and discovery boundary

The launcher gates the unchanged copied host, native libraries, full Linux input inventory and the exact versioned launch-layout manifest. ASL initialization is original code. The standalone probe also calls original `ASL_SetCurrentDir("C:\\Emu\\AppAssets\\Base\\Binaries\\Linux")`, records its bool result and records the kernel's actual cwd. It normalizes the original relative `../../../Base/Assets/Database/Modding.sql` through original `ASL_EmuToNativePath` and measures original `Platform::PathExists`.

A whole-tree `steamassets/base` symlink lets absolute emulated asset paths work, but the kernel resolves cwd into the original asset tree. That physical cwd falls outside the registered launch-root prefix, so original relative paths do not necessarily reverse-map into the emulated namespace. The v2 fixture constructs a genuine Base context, but `Modding::Framework::GetDatabase()` is null and XP2 configuration cannot resolve its requested mod. An unavailable native connection is reported as unavailable, never as a zero discovered-mod count.

The v3 fixture `../c6-ghidra/evidence/linux-rules/asl-launch-xp2-2` adds an actual private `steamassets/base/binaries/linux` directory skeleton and only aliases the leaf asset tree. The measured kernel cwd stays under the registered launch root and original relative Modding.sql existence is true. Before genuine TempHeap startup was restored, this exposed an original framework constructor allocator failure. That failed profile remains preserved separately from the successful startup measurement below. The source assets are unchanged; v1/v2 fixtures are retained separately.

The first invalid access has now been isolated, before any saved configuration is restored. Native mod discovery is parsing `../../../Base/Assets/Scenarios/tutorial/tutorial.civ6map`. Immediately before the copy, original `Modding::Path::GetFileName` requests 228 bytes, the fallback allocator rounds that to 240, and both original global TempHeap base and capacity are zero. The method passes the byte count unchanged as a wchar capacity; original `wcslcpy` delegates to libc `wcsncpy`, which pads 228 wchar_t values (912 bytes). Memcheck catches the first four-byte write immediately beyond the 240-byte block. The later native SQLite metadata-query allocation detects the resulting tcache corruption. This is evidence for a missing original allocator lifecycle prerequisite, not grounds to enlarge this buffer or patch the original copy routine.

Original `AppHost::_INTERNAL::SetupFXSPlatform` calls `GetTempHeap()->Startup(size,NULL)` at `0x42b4d94`. Both the original RunApp default and `Civ6App::OverrideAppOptions` set that size to 16 MiB. The heap is the actual process-global object at `0x6eef840`, not a thread-local substitute. Allocate first tries the original arena; the last DeAllocate releases its native lock and resets its cursor. Original platform teardown stops performance events and the job manager before shutting down this heap. The common host-service owner now runs that original startup before constructing App/providers and verifies ownership with actual native allocation/release operations. [Bounded contract evidence](../evidence/linux/mod-activation-tempheap-contract.json) records exact module and instruction-range hashes, signatures, the paused failing input and private diagnostic hashes. Global temporary-heap readiness does not establish GameCore state or gameplay parity.

With this prerequisite linked, the same v3 constructor profile now returns success: the original framework database contains **35 Mods rows, including the XP2 GUID**, and the active context vtable belongs to the exact Base SO. Original framework/controller/client/localization/Lua/App/FileQuit cleanup completes; the actual TempHeap has zero locks/cursor before original Shutdown and its native fields clear afterward. [Native discovery evidence](../evidence/linux/mod-activation-native-tempheap-discovery.json) records the complete gated configuration and diagnostics. This run restores no saved configuration and proves neither XP2 activation nor an initialized game. The previously minimized fallback overrun remains an original-code behavior observation; restoring its expected arena avoids that fallback in this fixture without changing the copy implementation.

When the native framework has a database connection, the adapter's diagnostic queries its original SQLite handle for actual Mods rows and the requested XP2 ID. These are read-only counts against the native modding schema; they do not create registry rows or infer eligibility from the supplied descriptor inventory.

## ConfigureContent and the genuine action pipeline

`ConfigureContent()` (`0x337f600`) returns an **eight-byte ConfigureContentResult aggregate in RAX**, not bool. Its constructor initializes five defined flag bits; bit zero is success and the upper u32 is the status code. An early bool interpretation of a noncanonical AL value was invalid and is excluded from passing claims. `UpdateContent()` (`0x3381860`) likewise returns an eight-byte aggregate, with three defined flag bits. Native caller tests, constructors and the decompiled aggregate returns establish these boundaries.

The exact Linux benchmark configuration is restored by original `Serializer::Manager::LoadConfiguration`; it reports RULESET_EXPANSION_2 and one enabled/required mod, `4873eb62-8ccc-4574-b784-dda455e74e68`. This proves restored host configuration, not successful activation. In the v2 fixture original ConfigureContent returns failure with status code one and retains the Base module path. The request could not be resolved through its unavailable mod database.

The v3 fixture with genuine TempHeap startup advances this request further: saved configuration restoration returns successfully, then original ConfigureContent reaches `ImportImplicitFiles` / `AppFileService::GetModPackage` and faults at `ContentPath::Manager::FindPackage` (`0x2f4e183`) with a null manager receiver. It returns no aggregate result. [Native failure profile](../evidence/linux/mod-activation-native-configure-contentpath-boundary.json) preserves that unsuccessful boundary; the private debugger trace records the actual null receiver, rather than inferring an interface from a slot.

The opt-in `--content-paths` diagnostic calls original whole `Civ6App::SetupContentPaths()` (`0x2f92a20`) after original option registration. That method forwards the original environment/options and an original OptionSet string to `ContentPath::Local::Startup`, which creates and publishes its real manager and native definitions/packages. It then reaches another missing host startup prerequisite: `SetupCommandLineOverrides` reads the AppEnvironment argc/argv pair, which the standalone App constructor does not initialize. The measured fault is the original argv-index load at `0x2f4f493`, before framework initialization or saved restoration. Original `RunApp(int,char**,Application*)` writes its real inputs into those fields at `0x42b9aa3` / `0x42b9aa7`; no native setter has been identified. [Separate environment failure profile](../evidence/linux/mod-activation-native-contentpath-environment-boundary.json) preserves this failure. The diagnostic does not invent argument fields, bypass command-line overrides, or claim provider cleanup for this failed startup. Original startup orchestration is under review before this opt-in path can become a usable runtime prerequisite. Default framework initialization is unaffected by this flag.

The common host fixture now bridges the **actual intercepted CRT argc/argv** into exactly those original RunApp fields, guarded per App and validated on reuse. Environment is App+8, so environment+0x28/+0x30 and App+0x30/+0x38 identify the same storage. The standalone probe exports the same captured-argument getter as the runtime fixture; it invents no argument string. With this common prerequisite, whole original SetupContentPaths and full framework/provider cleanup pass on v3. The next separate restored-XP2 Configure profile reaches original settings application, then fails at `Application::Data::LocalizationDatabase::GetDatabaseConnection` (`0x3042310`) with a null receiver from `ModdingMapSettingHandler::BeginApplySettings` (`0x3399796`). The independent dictionary fixture is genuine but does not create the App-owned LocalizationDatabase needed here. After the App-owned LocalizationDatabase bridge was added, Configure reaches UI art settings and throws `bad_function_call` through the uninitialized native `ArtLoading::ArtLoadingAllocator::allocFunction` (`0x65052c0`). The first throw stack goes through the custom allocator string in `ArtDefProvider::CreateConsumer`, then `ModdingUISettingHandler::ApplySettings`. [Preserved failure](../evidence/linux/mod-activation-native-art-allocator-boundary.json) records this boundary separately.

The opt-in `--art-manager` prerequisite calls original whole `Civ6App::SetupArtManager` (`0x2f95a20`). Original `ArtDefProvider::Startup` installs its allocator callbacks through native `SetAllocator` bound to the actual provider's `ChunkedAllocator`, then loads native base art definitions. A separately gated `--update-constructor-callback` diagnostic now constructs the real native `LoadGameViewState` (original SetupGameStates allocation size `0x4f0`), invokes the actual original inline callback constructor at `0x2fd62d0`, and enters original UpdateContent. With that real owner, original UpdateContent returns flags 3/status 0, the native callback/LoadGameViewState cleanup returns, and the actual active context vtable belongs to XP2. The later saved-configuration teardown fault is now attributed to ownership: Core configuration map copies retain the actual host VariantManager, and the framework destructor's ShutdownConfiguration frees that owner before its later Core unload. The adapter now calls genuine `AppModdingFramework::UnloadGameCore` while host configuration is still alive, verifies native context release, then calls normal DestroyInstance and controller/provider cleanup. The actual original UpdateContent sequence, recovered from the Linux host, is:

1. ConfigureContent and discover the selected components.
2. BeforeContentChange, unload GameCore, then load the configuration-selected module.
3. Roll back the native base gameplay/localization transactions as appropriate.
4. WriteGameCoreDatabaseData and invoke the optional original callback if present.
5. ImportImplicitFiles, original `Modding::Framework::ApplyComponents`, further implicit-file handling, native database validation/transaction completion.
6. InitializeGameCore, AfterContentChange, ownership checks and completion notification; failure paths roll back content.

This sequence supplies real importer and eligibility code. It has not been replaced by a list of SQL/XML files or by the historical Windows 213-input recipe.

The UpdateContent argument is an actual `std::__1::function<void(Database::IDatabaseConnection1*, bool)>` object, passed indirectly in RSI. The original caller at `0x2fd4c7e` constructs it through native helper `0x2fd62d0`, capturing the real LoadGameViewState. Its call body ultimately invokes `App::Censorship::ApplyContentCensoring` with that view state's native `+0x4b1` setting. UpdateContent checks callback presence before invoking it. The adapter does not forge an empty std::function, substitute a C function pointer, invent the view-state flag or bypass censoring. A genuine original caller/object lifecycle is still needed to execute this stage.
