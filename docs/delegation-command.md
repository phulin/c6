# Bounded delegation command

`c6_data::loaded_actions::session::Session` supports a human sender's delegation command at an initialized AI recipient's external accept/refuse decision, and an AI sender's proposal to the active local human. This is a bounded Linux XP2 command path; complete Civ VI state, arbitrary actions and full turns remain unimplemented.

Build `delegation_actions::Definitions::from_rules` from the same rules and state, then call `request_diplomatic_delegation(sender, recipient, definitions, configuration)`. `pending_delegation()` identifies the recipient and its two choices. The recipient can respond while inactive; it does not acquire an ordinary player action or end its turn. Other actions and turn progression refuse the pending boundary.

`respond_diplomatic_delegation` takes the external response, the current effects provider and ordinary `TurnServices`. It preserves the initialized recipient's partner-action closed flag update for either response. An affordable acceptance debits the sender, delivers gold callbacks, establishes the delegation and its callbacks, rechecks diplomatic visibility, then credits the recipient and delivers its gold callbacks. The setter emits its signal even for an already established delegation. Costs use current game-speed scaling and purchase-divisor rounding; balance changes clamp as in the native treasury.

The command message then performs its required single `Game.Update`. A reached policy choice returns `Progress::Choice` and retains the outcome. Resolve the current choice through the existing Session policy API, then call `resume_diplomatic_delegation_update`. Completion returns `Progress::Complete`; it does not imply a completed turn. Pending decisions and update continuations remain on the existing backend when extracting and rebuilding Session parts. Callback failures retain the affected prefix and make the Session fail explicitly.

The effects provider must execute current gold, delegation-established and visibility callbacks against the same gameplay, modifier and RNG owners. Missing provider support is an error; there are no successful default callbacks. The original engine is not a production dependency.

This surface executes the `SetDelegation` command. It does **not** implement the broader diplomatic UI offer query or complete legal-action enumeration. Its supported endpoints are met, peaceful, alive majors with a human sender and initialized AI recipient. Multiplayer, uninitialized diplomatic response handlers and unrelated action branches remain unsupported. Representative Linux comparisons passed for ordinary, affordable acceptance and refusal from initialized two-capital fixtures. They matched all compared typed gameplay/player fields, the partner-action cell, requirement/modifier changes, diplomatic visibility, logical session state, the mandatory update, and the reached gameplay RNG and libc streams. Acceptance includes the standard delegation opinion modifier and ordered callbacks. These are bounded profile comparisons, not complete diplomacy, legal-action enumeration or whole-game equivalence.


For an AI sender and the active local human recipient, use `request_diplomatic_delegation_to_human` with current capability membership, a required `stock_notifications::delegation_human::Effects` report/close provider, and ordinary Update services. This keeps the initial human-target statement route: its original command Update reaches `Progress::HumanDecision` and the actual rules-derived Positive, Negative and Exit choices. The sender may be inactive; this diplomatic command grants no ordinary inactive-player action or turn.

`respond_human_diplomatic_delegation` executes the selected response. Positive and Negative preserve different response/acknowledgment subtypes, but **both send the embedded delegation enable command** in this Linux profile. Both therefore debit an affordable sender, establish the delegation, credit the human recipient, preserve ordered callbacks, clear the sender evaluator's two delegation cells, and execute the mandatory embedded-command Update. Neither writes the recipient's closed-partner-action cell. Initial Exit closes without sending that command. The acknowledgment's sole Exit option runs as a deterministic close continuation after Update, retaining complete logical closed history. No StatementResult action is substituted.

A reached Update policy returns `Progress::Choice`; resolve it with the existing Session policy API, then call `resume_human_diplomatic_delegation_update`. Callback failures preserve the affected prefix and fail the Session. The current implementation requires a fresh, observed manager session inventory and the correct initialized AI sender evaluator. Representative Linux comparisons pass for Positive, Negative and initial Exit, including the initial decision, all compared typed gameplay/player fields, source-ordered callback effects, exact requirement/modifier transitions, logical closed history, pending-action inventory, mandatory Updates and reached gameplay/libc RNG. Both existing human-to-AI accept/refuse regressions also pass on the same optimized artifact. Human-to-human and other control profiles remain unsupported; this extension does not establish complete diplomacy, arbitrary actions, full turns or whole-game equivalence.
