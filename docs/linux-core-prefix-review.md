# Direct Rust Core prefix review

The direct Rust prefix milestone through complete Map is accepted at `f531a46`, composing Map prefix refactor `7e36363`, reader `96808f6` and export `2eac8b0`. No concrete defect was found. The reviewed immutable offline candidate is `15143093b47948c067db1aeb901002b857df471f4bb2dfba634d05b361f610d2`. This is a bounded raw-wire prefix reader; metadata compatibility, native Load side effects, full Core/Player import, RNG and gameplay remain unsupported. Identities and results are in [core-prefix-review.json](../evidence/linux/core-prefix-review.json).

The library starts at raw Core byte zero and consumes framed metadata, current IndexSerializer/Game/Rules versions, the supported Placement provider, all three processors, Game scalars/properties and complete Map. It neither accepts caller-provided Map offsets nor consults Python, native traces or game code. Unknown unframed Rules providers/counts are refused. Processor arrays retain all original uncounted 64 entries, signed values, update counters and bools; phase segments retain wire order and hashes. The three GameProcessor bools correspond to the original Game namespace globals, not inferred object offsets. No AI-labelled serialized field is excluded.

The Map prefix wrapper reuses the strict decoder body, clips only to the caller's consumed-byte policy, reports actual consumption/items and permits a caller tail. Strict Map decoding and range collection retain their prior exhaustion and limit behavior. The enclosing reader subtracts prefix item and logical-allocation charges before calling Map and stops immediately after Map. Variants share remaining byte/item/depth limits and receive the same conservative allocation charge as Map. Fixed processor arrays consume item credit but do not claim heap allocation. Checked arithmetic and successful-read invariants protect the remaining-credit subtractions and input slices.

The result owns typed prefix values and borrows the original tail at `map_end == consumed`. No full tail/world copy is used by the parser. A complete Map with no following bytes is a valid prefix result; this does not establish a complete Core stream. The next real unparsed serializer is Game.Religion. Tail contents do not affect decoded prefix values and remain unclassified gameplay/state dependencies. Provenance and active rules/configuration gates remain caller responsibilities; accepted metadata bytes do not prove native compatibility or admission.

Independent validation checked the candidate hash, all 50 archived source identities, 42 original method fingerprints and the three native Game bool symbols. The immutable executable then received both complete 80,657,462-byte original raw streams. Every metadata/processor/phase/Game scalar/property value matched the separate Python grammar. Map was found dynamically at 1,884..4,695,864 and re-encoded to the exact 4,693,980 original bytes, SHA-256 `cd2ec75b4e342a6ebccc1b96889335352657b9ea67f83d5f6d56f6a94eaf2de9`. Each 75,961,598-byte tail retained its original pointer and digest. The 89,198-byte raw difference between the two streams remains unmasked; they are one normalization context rather than independent gameplay branch diversity.

Four focused Core reader tests and the Map prefix regression test passed. A separate Rust harness verified the native record's shared budgets: 1,957,345 Map items plus 751 prefix items require exactly **1,958,096 items**. Map's minimum logical-allocation charge of 5,253,460 plus prefix charge 10,296 requires exactly **5,263,756 bytes**. The combined exact byte/item/allocation limits succeed; reducing any by one fails. The byte limit is the consumed 4,695,864 bytes and excludes the borrowed tail. These are caller-policy logical charges, not measured allocator usage or native memory layout. Sample actual-prefix truncations and an unknown provider were refused; replacing all tail bytes preserved the typed prefix.

Source-only cases rechecked the 20-byte metadata and 24-byte Game-property relocations. An additional independently constructed case appends a five-byte `(hash,bool)` phase segment and increments its count: Map start/end move by five, while Map bytes and the untouched tail remain equal. Existing tests also cover repeated phase hashes, bad versions/providers/bools, truncated source carriers and unknown Map components. These are framing/limit tests, not native gameplay or metadata-compatibility observations.

No original game execution, native rerun, Ghidra write, private upload or UI-admission change was performed. This review preserves the historical candidate and all earlier City/movement identities. Further import must consume the real intervening schemas and reconstruct required live state; preserving an untouched tail does not permit advancing it.
