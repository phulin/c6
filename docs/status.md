# Implementation status

The supplied Windows XP2 FinalRelease DLL remains the existing tested behavioral baseline. Linux has richer symbols and a working native context lifecycle, but its relative age/currentness is unverified. The proven layout difference requires separate profile validation; it does not establish chronology. Linux may become the primary execution path after the provenance/version audit. [Profile policy](targets.md) and [reference-reuse evidence](reference-reuse.md) define the evidence boundary.

As of 2026-11-02, c6 provides a tested Rust kernel for isolated RNG, geometry and action-message transport, a loadable C ABI, and an original Windows DLL bootstrap running under Wine. Genuine native contexts initialize with original database fixtures and complete the context-only lifecycle. With additional genuine script providers, original StartupGame returns and the first original Load enters game-state initialization, where required host-service boundaries are still being resolved. It does not yet provide the requested complete headless Civilization VI simulation. No complete player-action sequence or end turn has been reproduced.

Two Windows-oracle execution paths serve different purposes. The isolated mapper executes bounded original methods using synthetic objects and documented stubs; it does not run DLL initialization. The Wine bootstrap loads the whole original DLL normally and invokes genuine context interfaces with explicit host services. The mapped original host executable supplies specific verified code paths; its entry point and global constructors are not run. Neither path establishes complete gameplay parity.

The declared Base/XP2 recipes use original SQL/XML importer, hashing and embedded GameCore database code. They do not execute the full mod-selection resolver or prove equivalence to the saved session. Native transactions, measured row mutations and foreign-key results matter independently of method return flags. Two native builds export identical rules databases; `c6-data` verifies their complete pinned schema and typed rows. These pre-startup artifacts are rules inputs, not a game-state snapshot or a mapping from SQLite row IDs to GameCore definition IDs. See [content evidence](assets.md), [rules snapshots](rules-snapshot.md) and [Rust rules data](rules-data.md).

Original localization, genuine App/gameplay-database and script providers now support StartupGame returning, followed by context destruction/unload with verified empty-only job-set cleanup. Full DLC/mod localization and job scheduling remain unsupported. Original Load records native stream position while required logging, options and job-service contracts are checked against current Windows code. Its latest boundary is retained in [native runtime](bootstrap-runtime.md), [host services](bootstrap-services.md) and [save loading](save-loading.md); no successful Load or complete restored state is established.

The native RNG payload remains distinct from the custom `C6SN` envelope and Civ VI saves. Short streams and nonzero legacy flags are refused before native reads; raw synchronous-byte values above 1 can round-trip in serialized records but cannot be applied to Rust boolean state. Likewise, exact action-message serialization does not validate action legality or affected gameplay state.

## Next concrete milestones

1. **Complete native game startup and load a pinned fixture.** Preserve the successful declared XP2 content and embedded GameCore database phase, then establish the saved session’s live configuration and authentic mod-selection order. Continue original Load through the observed service boundaries using current-Windows contracts, preserving native stream-position observations and scheduling limits. Verify a successful Load result and complete affected state before treating the fixture as restored gameplay. Preserve saved configuration, DLC/mod ordering, rules identities and complete stream observations. A returned context Initialize flag is insufficient.
2. **Audit a complete state boundary.** Inventory world/map, players, units/cities, component containers, stable IDs, pending events, turn scheduler, caches with semantic effects and every random stream. Determine canonical serialization and restore behavior. Opaque sections preserve data but cannot substitute for this audit.
3. **Implement one real legal action end to end.** Select a small operation from the verified dispatcher, recover its parameters and legality conditions, execute it in the initialized native fixture, and compare all affected state and RNG before adding Rust support.
4. **Reproduce a minimal complete turn.** Establish the actual completion message sequence, iteration/event order, delayed updates and all random streams for a constrained fixture. Compare state after each meaningful boundary and after turn completion. Processor method names alone are insufficient evidence of a complete transition.
5. **Expand configuration coverage and measure useful workloads.** Add rulesets and interacting systems only with pinned fixtures. Measure action and turn throughput once those paths exist; current RNG timing cannot predict it.

## Checks and evidence

The project checks Rust state/geometry/RNG behavior, serialization and message codecs, FFI contracts, harness failure handling, a compiled C consumer and original-DLL comparisons. Separate [bootstrap checks](bootstrap-validation.md) verify original context lifecycle, database diagnostics and identity rejection; later content/startup observations have their own evidence records. Run the commands in [README](../README.md) to reproduce the checks with the required local binary. Test counts and timings may change as coverage grows; [architecture](architecture.md), [oracle](oracle.md), [differential protocol](differential.md), [performance](performance.md) and [reference provenance](reference.md) define what each result establishes.

The [engine dependency roadmap](engine-roadmap.md) records the concrete bootstrap services, message-dispatch edges and bounded next investigations. The main unresolved dependency is progression from the verified native context/data bootstrap to a reproducible initialized gameplay session, including authentic content/configuration, successful save-state restoration and complete lifecycle teardown. The read-only [Linux installation inventory](engine-roadmap.md#incoming-linux-installation) can identify supplied ELF binaries and their dependencies; the matching `Civ6` host, `libGameCore_XP2.so` and installation data are needed to investigate that separate platform. Complete state extraction and all gameplay semantics remain substantial implementation work. Neither the recovered symbol map nor the existing primitive corpus closes those gaps.
