# Original application database provider

The headless fixture now executes the complete original Civ6App constructor and GameplayDatabase constructor, opens the actual populated gameplay database through the original URI factory, prepares the original GlobalParameters statement, and creates/removes an original `GameCore_Tuner` Havok script state. This is a bounded original-code result. It does not execute full AppInit, initialize a game, validate script callbacks against a complete game, or establish action/turn parity.

`python3 tools/analysis/app_provider_probe.py` checks every supplied module/runtime identity in `tools/bootstrap/config.json`, checks the actual native gameplay snapshot against the published snapshot SHA-256, builds an isolated child and records source/header hashes, executable hash and configuration identity in [app-provider.json](../evidence/bootstrap/app-provider.json). The child restores the private native snapshot with original DatabaseDLL `CopyFrom`; it does not generate rules content. The source snapshot must first exist at `../c6-ghidra/evidence/rules/run-1/gameplay.sqlite`. The full content recipe remains the authority for how that snapshot was populated.

Original EXE caller RVA `0x79c7b` allocates `0x5890` bytes with allocator `0x982060`, calls Civ6App constructor `0x5ccb0`, then publishes its result to singleton `0x12c2c88` at `0x79c95`. The helper invokes that exact allocator and complete constructor, verifies vtable `0xfa5be0` and initially null `+0x54d8`, then explicitly publishes the genuine object at the verified singleton location. It does not invoke caller `0x6fef30`, which begins the application's broader lifecycle.

Original AppInit allocates `0x40` bytes at `0x718d1`, calls GameplayDatabase constructor `0xbf070`, and installs the result at App `+0x54d8` at `0x718f4`. There is no independent setter among the target instruction references to this field. The helper therefore performs this installation explicitly as headless fixture ownership wiring, only after checking that the destination remains null. The actual constructor installs vtable `0xfb3410`, initializes its native fields and generates `file:gameplay-0?mode=memory&cache=shared`. The helper verifies that exact URI, then calls original connection factory `0xbf6a0` with the genuine wrapper's connection slot as its output parameter. This also uses the actual original logging-manager lazy creator; no logging-manager shell is introduced.

The attachment requires the already populated original gameplay connection as an argument. Both connections must have the expected original DatabaseDLL interface identity. Native SQL queries compare every table's row count and total table count against that source, reject an empty source, and record an FNV-1a digest of sorted table names and their row counts. The validated snapshot has 428 tables and 41,704 rows, with count digest `d59b1e0bd123675f`. This digest is explicitly a table/row-count digest, not a complete content hash; the native snapshot's separate SHA-256 identifies its full bytes. The helper prepares the exact original SQL at EXE `0xfb3570` through the original connection's statement API and records the native database change count, matching the original wrapper initialization tail. It does not rerun wrapper schema/bootstrap file parsing over the populated database.

The constructor helper and attachment helper independently verify the EXE hash. Attachment additionally verifies the DatabaseDLL hash and original connection vtable identity. Callers must preserve the configuration gate for all other supplied modules and runtimes. The native probe subsequently runs the original ScriptSystem helper, invokes its real slot `+0x00` with narrow `GameCore_Tuner` and true, checks for a nonnull state, and invokes real slot `+0x08` to remove it. This passes the previously failing native GameInfo callback at `0x2a3504` and App database getter `0x64660`.

Ownership remains explicit: the actual App owns its installed wrapper; the wrapper owns its connection and cached statement. The source keepalive is a separate reference and must remain alive throughout attachment and execution. The current probe uses isolated process exit for App/wrapper/log-manager teardown; their complete destructor sequence after this partial application lifecycle is unverified. The original script state is removed before exit. Do not independently release the wrapper's connection or cached statement, free the App storage, or claim reusable lifecycle teardown from this probe. On setup failure the child exits rather than presenting a partially configured application as success.
