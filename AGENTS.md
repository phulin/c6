# Working on c6

The objective is an exact headless Civ VI state/action/turn library, checked against original Linux game code. The current Rust implementation covers bounded primitives, wire transport and rules/registry components; complete gameplay state, action execution and turns remain unimplemented. Keep that distinction explicit in code, docs and completion reports.

## Feature delivery

- Prioritize complete, usable features. Follow a short loop: inspect the relevant original code, implement the feature end to end, check representative native parity, then move to the next feature.
- Investigate and capture only what a concrete implementation or comparison failure needs. Source audits, provenance machinery, save parsing and notification internals support feature delivery; they are not independent completion goals.
- Keep uncertainty and unsupported branches explicit, but do not require closure of every surrounding system before advancing a supported feature. Preserve affected gameplay state, pending decisions, callbacks and RNG; defer unrelated unknowns with a clear scope.
- Reproducibility needs the target/rules identity, canonical input paths/hashes, exact committed public/private source hashes including every compiled change, command, build profile and actual result. Commit compiled changes before comparisons and keep those commits reachable; do not retain per-run source archives, extracted repository copies or patches. Reuse existing harnesses and checks; do not add repeated admission, audit, source-archive or release gates.

## Repository layout and workflow

- `c6` is the public repository for the final simulator: production Rust libraries, the C ABI/header, production build/interface checks, synthetic regression tests and user-facing documentation. New reverse-engineering tools, source audits, original-engine oracle/harness code, investigative reports and captures belong in private `../c6-re`.
- Private `../c6-re` owns the investigation and validation workspace, including original-engine adapters, differential candidates, source-audit scripts, evidence, capture provenance and private fixture tests. It may depend on an explicitly pinned public `c6` tree; public production builds must not require the private repository or its captures.
- `../c6-ghidra` is reserved for annotated Ghidra databases/projects and the files required to preserve those projects. Non-database investigative tools, reports and captures belong in `../c6-re`. Preserve existing evidence identities and history when relocating files; changing a path does not create a new observation or repair an old validation gap.
- Mainline work belongs on `main`. Clean up merged temporary branches only after the coordinator verifies that their approved commits are retained; do not discard unmerged work or rewrite shared history.
- Coordinate shared-file changes and preserve untracked and concurrently staged work. Keep dependencies and public/private boundaries coherent. Use committed checkpoints for handoffs and verify public builds without private siblings; record the code pins used by a comparison.
- Root coordinates shared work. `reference_reuse` remains the sole original-engine runner and repository publisher until reassigned. The repository migration is complete; ongoing Linux comparisons and authorized pushes proceed with pinned targets and reproducible inputs. Avoid duplicate original processes or concurrent publishers. Do not perform bulk moves or branch cleanup as an incidental part of unrelated implementation tasks.

## Task coordination

- Use a separate `gpt-6.1-sol` agent at `medium` reasoning effort for each individual implementation or research task, as requested by the project owner. Give each task explicit file ownership and a concrete result. Use a fresh context when selecting the model/effort.
- All agents share the checkout. Check `git status` before editing or committing; stage only owned files. Every commit must use `git commit --only -m "message" -- explicit/owned/path ...`, even after earlier staging: another agent may stage files concurrently, so a bare commit is insufficient. Preserve other agents' staged and untracked changes. Coordinate shared manifests, protocols and evidence identities; never discard another agent's edits or use broad staging.
- If an owner-approved file is accidentally captured in a shared-index commit, preserve the approved history and coordinate a scoped follow-up. Do not rewrite shared history to repair that inclusion.
- Task owners may add necessary module exports and narrow accessors for their assigned work after checking direct file ownership. Coordinate with any active owner, preserve unrelated WIP, and commit only owned paths; repeated root permission is not required.
- Keep coordination concise. Put raw disassembly, decompiler dumps, captures and long investigative tool output in private `../c6-re`; reserve `../c6-ghidra` for annotated Ghidra project/database artifacts. Send the coordinator only conclusions, relevant addresses, evidence paths, checks and blockers.
- Commit coherent, validated checkpoints and push the authorized project repositories. Coordinate the current public push writer and report commit IDs and unresolved gaps. Ghidra project commits require a clean save/close before snapshotting; follow private `../c6-re/docs/ghidra.md`.
- Designate one private-repository push owner at a time. After committing immutable closed-project snapshot chunks, release snapshot-write ownership so other verified descendants can be prepared; batch those descendants into one push. Do not launch duplicate concurrent uploads of large snapshot packs.

## Exactness and evidence

- The user explicitly defines the simulator as yielding to external policies for **all player decisions**. Execute exact rules/upkeep between decisions and yield at the next genuine decision boundary; native AI policy choices must not silently fulfill actions or end turns.
- The target is an AI arena with exact gameplay state, legal decisions, callback effects and RNG. Native notification/UI objects, pool/cache layouts and presentation output are not goals in themselves. Inspect the effects reached by the feature, preserve gameplay/RNG effects, and emit or omit presentation output at the headless boundary. Preserve every reachable RNG draw, stream identity, order and state even when surrounding presentation work is omitted; do not infer no RNG or no gameplay effect from a UI namespace or unchanged endpoint samples. External policies need semantic pending decisions and legal-action information, not native UI policy execution.
- Exact gameplay state and gameplay RNG remain in scope. Omit policy selection; preserve gameplay updates, diplomacy, deals, NPC state and relevant RNG even in AI-named code.
- Complete Civ VI save parsing is optional fixture-import functionality, not a prerequisite or acceptance gate for actions or end turns. Prioritize a first complete action from an original-engine-initialized or loaded fixture plus a typed snapshot. Extend parsing or capture only for a concrete gameplay dependency. Production remains standalone Rust; the original engine is an oracle and fixture producer, not a production runtime dependency.
- Civ VI save production and binary-identical save rewriting are not success requirements or action-acceptance gates. Native Save output and roundtrips are decoding diagnostics and omit unsaved runtime state; acceptance still requires all affected gameplay state, RNG, ordering and logical identity to match. Keep unknown save bytes unclassified and unmasked, and retain raw Save→Load differences, including the recorded 89,198-byte failure. Proven serialization-only differences do not block live action implementation; unresolved gameplay effects remain validation gaps. A planning-only exclusion must be evidenced rather than inferred from a byte range or class name.
- The user directs Linux-only execution and acceptance for the complete state/action/turn goal. Target supplied `libGameCore_XP2.so` SHA-256 `a0b6611f45ed28fa7bf6e18d608cafddbdd5b1c20cfd880cb50937af731c1faa` with matching Linux host, dependencies and inputs. See `docs/targets.md`.
- Preserve Windows code/evidence as frozen historical work. Do not start Windows-specific tasks, run Wine/Windows native tests, or extend Windows validation unless the user changes this direction.
- Keep exactness and coverage profile-specific. Historical Windows RNG/geometry/message and rules-data parity cannot count as Linux support; validate against original Linux code and export actual Linux rules inputs. Do not reduce the full objective to a lifecycle or primitive subset.
- Linux/Windows layout differences do not establish relative age. Use symbols/DWARF and the pinned reference for discovery, then validate reused contracts against the Linux target's bytes and native fixtures. Public-depot identity, shared names and Steam build numbers do not establish cross-platform behavior equality.
- Never represent approximate mechanics, placeholder actions, opaque bytes or a toy simulator as exact Civ VI behavior. Never treat unsupported behavior as a no-op or success. Expose incomplete transitions and their state explicitly; public callers must not mistake partial state for a completed action.
- Gate original-code execution by exact module SHA-256 and configuration identity. Record the rules database, enabled DLC/mods and configuration for any future initialized game fixture. RVAs, old symbols and Linux layouts are evidence leads until verified for the target binary.
- Check an added operation against the target version with representative native inputs and compare its outputs, affected gameplay state and RNG. Add boundary cases where they expose real risks; preserve useful failing cases. Do not infer complete subsystem or turn equivalence from a primitive test.
- Preserve deterministic ordering, wrapping arithmetic, stream identity and complete RNG state. Do not substitute a host PRNG. Keep logging/service stubs and synthetic object fields documented as limits of the test context.
- Keep simulator state transport distinct from actual Civ VI save loading. Retaining unknown sections does not establish their semantics or permit advancing them correctly.
- Preserve attribution and license boundaries for acquired reference material. Do not commit proprietary DLLs, game assets or private Ghidra project data to this public repository.

## Validation

Run checks appropriate to the changed boundary. The common commands are:

```sh
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
bash tools/check/c_abi_smoke.sh
```

Use the native and differential checks owned by private `../c6-re` when changing supported mechanics or their adapters, verifying the pinned target and configuration before execution. The private workspace owns the relocated checks and their complete dependencies; public production checks must run independently of private siblings. Bind each comparison to the actual candidate executable and its reproducible input corpus and configuration. Run focused checks, execute the comparison, and preserve honest failures and the inputs needed to reproduce them. Separate helper-level reports, admission stages and per-batch releases are not required. An unavailable oracle is a validation gap, not a passing comparison. Benchmark only implemented behavior and report what the measurement excludes.

For a comparison, retain the target/rules identity, reproducible input, code pin, command and actual result. Commit all required compiled changes before comparing and record the exact public/private commits; keep those commits reachable from branches or tags. Do not retain per-run source archives, extracted repository copies or patches. Keep historical failures and limits honest.

Reuse compatible Cargo targets; do not retain permanent per-run targets, duplicate executables or dependency trees. Never recursively copy the workspace into artifacts. If isolation is needed, temporarily export only explicit committed build inputs, excluding artifacts, captures, archives, Git data and compiler outputs; remove temporary sources in a context manager, finally block or shell trap. Retain each required input state, runtime observation, rules/configuration input and unknown captured byte once at a canonical path with a hash, referenced by small result reports. Add captures only for concrete gameplay/RNG dependencies or observed failures. Historical cleanup is separate: identify provenance and dependencies before deleting unique binaries or source, and do not replace validated captures, rewrite results, bulk-delete historical artifacts or rewrite history. When disk headroom is low, remove only inactive incremental compiler caches after excluding active targets.
